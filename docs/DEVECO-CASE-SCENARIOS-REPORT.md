## 结论（按场景类型的收益规律）

1. **收益和场景"读多少、diff 多少"强相关**：
   - **代码审查 / 重构 / 回归排查 / 代码考古**——大量 `git diff/log` + 读多文件 → saved 高（8k–26k），e2e 超过 1%。
   - **小改一行（转义/补测试/文档/依赖/单点修复）**——几乎没大输出 → saved 恒为 ~437（**一次 SPEC.md 的 read-CCR**），e2e ~0.06%。
2. **437 tok 是一个"会话固定成本"**：每轮 agent 都会 `read` 一遍 SPEC.md/ISSUES.md，read-CCR 每次省 ~437 tok。小改轮次的收益基本就是这 437。
3. **git 类是 TSK 最稳的提款机**：轮 11 回归排查（git log/diff）、轮 16/18（diff 审查）都靠它。
4. **read-CCR 的增量贡献**：23 次 `cat <path>` 共省 30,659 tok（占全量 35%）——集中在 SPEC/template/大文件整读；代码考古（轮22，73 秒）e2e 1.57% 就是 read-CCR + 小会话分母的双重效果。
5. **2–7 轮为什么是 0**：agent 改代码但不跑构建（harness 已修提示词强制验收后，轮 8 起显著改善）。

## 方法

- 同一种子 → 22 轮连续演进（git 每轮提交，历史累积供回归/考古用）。
- 度量：`<seed>/.tsk/injections.jsonl` 的 `sandbox-output.saved_tokens` 逐轮求和；e2e% = saved / 该会话 input（`deveco export`）。
- 完成度：`verify.sh`（后端测试 + 前端产 hap）+ 独立验收 `acceptance/run.mjs`（15 项 HTTP 契约）。

## 压缩通道构成（2026-10-16 从 journal 49 次事件实测拆解）

88,995 tok 的实际来源（**口径提醒**：`read` 工具经 read-CCR 复用 `cat` 分支，journal 里 `command` 字段被记成 `cat <path>`，但 `tool` 字段是 `read`——两者要分开看）：

| 通道 | 次数 | saved tok | 原始字符 | 压缩率 |
|---|---|---|---|---|
| **git diff/show** | 9 | **34,451** | 140,407 | **95%** |
| **文件整读**（read 工具 26 次 + bash cat 1 次） | 27 | 36,031 | 168,201 | 79% |
| hvigor/devecocli build | 12 | 11,701 | 57,725 | 80% |
| bun test | 1 | 6,812 | 28,495 | 76% |
| — 按 `tool` 分：bash 23 次 65,125 tok / read 26 次 23,870 tok | | | | |

**三点关键结论**：

1. **git diff/show 是性价比最高的通道**——95% 压缩率，9 次换 34,451 tok，且是每轮自然产生的成本（不需要模型刻意做什么）。
2. **文件整读里 19/27 次是同一个 `cat SPEC.md` @ 437 tok**（合计 8,303 tok）——这就是那 437"固定成本"的真相：**它不是每轮一次的固定开销，而是 `SPEC.md`(2,573 B) 被反复 cat 了 19 次**。小改轮之所以恒 437，是因为它们只有这一次压缩。
3. **单文件越读越大，收益越陡**：`SPEC.md` 2,573 B → 437 tok；`API.md` 9,823 B → 2,249 tok；`app/.hvigor/` 51,261 B → **12,161 tok**。`reference/books.json` 293,940 B 一次整读 ≈ **73k tok**，量级远超 22 轮任何单次。

> **度量盲点**：saved 只统计工具**输出**被压缩的量。若模型改用 `tsk analyze` 在沙箱内读大文件（输出很小），指标 saved≈0——即使上下文实际被省了。**设计高收益轮次时要逼出大输出，而非绕开读取。**

## 32–55 轮：配方 A（强制工具整读）+ 新数据源（2026-10-19）

继续冲高时发现最大杠杆不是阈值、不是更多小轮，而是**让模型用 cat/read 工具读全量文件**（而非写脚本 `readFileSync` 只打印统计）。27 轮失败 vs 32 轮成功（104k）的唯一差别，就是 prompt 里加了一句"**禁止写脚本解析，必须用 cat/read 工具逐段读完**"。

**32–47 轮（配方 A 应用于 books.json 294KB，16 轮）**：saved 480,540 / input 13.12M / 段内 e2e **3.66%**。单轮最高轮 33（85,810 tok，e2e 23.7%）。

**关键规律**：收益与"被读文件的字节数"近似线性（294KB→单轮 73–120k；1.4MB→单轮 160–563k）；大文件读本身 input 成本≈0（压缩后只进 ~200 token 摘要），saved 是纯赚。**全局 e2e 因此从 1.59% 跃到 3.92%**（55 轮总账 saved 3,127,784 / input 79.74M）。边界：1.4MB 已是真实借阅历史的合理规模，继续冲高只剩"堆更大数据"、会偏离真实案例，故收敛于此。
