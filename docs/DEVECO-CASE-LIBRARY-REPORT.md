## 三步跃升与配方设计指南

同一条工作流上，端到端收益经历了三次跃升——**每次都不是调参数，而是改任务设计**：

| 阶段 | 轮次 | 关键动作 | saved | input | e2e% |
|---|---|---|---|---|---|
| 基线 | 1–22 | 原始 backlog | 88,558 | 23.93M | 0.370% |
| ① 高收益轮设计 | 23–31 | 按压缩触发机制反向设计（审查/大重构/git 考古） | +109,532 | +23.30M | 0.470%（该段） |
| ② 配方 A：强制工具整读 | 32–47 | prompt 禁止脚本、强制 cat/read 读全量 | +480,540 | +13.12M | 3.663%（该段） |
| ③ 新数据源 | 48–55 | 引入 1.4MB `loans_history.json`（books.json 的 4.8 倍） | +2,035,296 | +10.99M | 18.5%（该段） |
| **全量** | **1–55** | | **3,127,784** | **79.74M** | **3.9224%** |

**核心发现（可复用的任务设计法则）**：

1. **收益只来自"被压缩的大工具输出"**，不来自"避免读取"。三道闸必须同时满足：输出 >1600 字符 + 命令被识别（或 hvigor/bun test 标记）+ read 需 `TSK_READ_CCR=1`。`tsk analyze` 在沙箱内读大文件→输出小→**零收益**（度量盲点）。
2. **配方 A（最强杠杆）**：让模型**用 cat/read 工具读全量文件**（而非写脚本 `readFileSync` 只打印统计）。27 轮失败 vs 32 轮成功（104k）的唯一差别就是 prompt 里加了一句"禁止写脚本解析，必须用工具逐段读完"。**大文件读本身 input 成本≈0**（压缩后只进 ~200 token 摘要），saved 是纯赚——所以 e2e 能到 20%+。
3. **收益与"文件字节数"近似线性**：books.json 294KB → 单轮 73–120k；loans_history.json 1.4MB → 单轮 160–563k。这是 e2e 从 1.6% 跃到 3.9% 的直接原因。
4. **git 考古轮收益 = 该主题被改动的密度**：借阅逻辑（31，47k）、测试（36）、API 契约（42）高；构建配置（44，4k）低——配置历史太薄。
5. **单轮 e2e 排行 TOP5**：轮 54（49.1%）· 轮 33（23.7%）· 轮 53（23.2%）· 轮 49（22.9%）· 轮 48（22.4%）——全是整读类。

**边界与诚实声明**：阶段③的高 e2e 依赖"更大的数据文件"，而 1.4MB 已是真实借阅历史的合理规模；继续冲高只剩"堆更大数据"，会偏离真实案例。**因此收敛于此**——55 轮 / 3.92% 是本案例在"保持数据真实"前提下的自然上限。
